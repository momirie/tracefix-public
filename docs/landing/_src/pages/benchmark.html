Tracefix is measured on real bug fixes from open-source Python projects: correct fixes, which should get no counterexample, and wrong ones, which should not look verified. Every number on this page comes from the committed runs, receipts and labels.

Method. And what the numbers don’t show.

The full method, the commands to run it again and every table: docs/BENCHMARK.md.

Tasks
Real merged bug fixes from SWE-rebench (Nebius, CC BY): each with a Docker image and hidden tests, the tests the upstream pull request added. At most {{per_repo}} tasks per project, in a fixed order, never hand-picked.
Fixes
Correct: the upstream fix, and agent fixes the hidden tests pass. Wrong: the upstream fix with one hunk removed (kept only when the hidden tests then fail), and agent fixes the hidden tests fail. The agent patches come from an OpenHands agent’s runs that Nebius published.
What Tracefix sees
What a reviewer would: the repo before the fix, the fix and the issue. Never the hidden tests: they stay out of every run’s container.
Checks first
Before any model call, a task must pass in its own container: the base suite passes within {{suite_cap}}, the hidden tests fail before the fix and pass on the upstream fix. A task that fails a check is left out, with its reason.
Runs
tracefix verify once per fix, in Docker, with strict isolation and a limit of {{verify_timeout}} per run.
Labels
The developer judges every finding the numbers count: real bug, false alarm or unclear. A model may propose a label; only the developer’s labels count.
Set aside
A counterexample whose only cause is a regression in a test the upstream pull request itself changed says nothing about the fix, so it is counted apart.

Caveats

  • Small numbers. One run moves a wrong-fix rate by several points. Treat every rate as a measurement in progress.
  • Development split. The newest numbers are from the tasks the next round of changes is tuned on; the gates are read on the held-out tasks after it.
  • One run per fix. A second run of the same fix can land on a different level, and now and then a different verdict.
  • One agent. Every agent patch comes from one agent setup. Other agents make other mistakes.
  • Seen before? The tasks are public and likely older than the models’ training data, so a model may have seen the fix or its tests.
  • A skewed sample. Only projects whose suite runs quickly in the published image qualify; large projects are not represented yet.
  • One person’s labels. Written down with reasons, and linked from every miss above.
