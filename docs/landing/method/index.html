Method

How Tracefix decides. A model proposes. Our code decides.

Tracefix uses models to write tests, plant bugs and propose what a function should promise. None of them sets a verdict. Every level in a receipt comes from an exit code, a diff or a counter that Tracefix’s own code produced. This page is how, and where it stops.

The rule. AI proposes, deterministic code decides.

A model’s answer is a proposal: a file to run, an edit to try, a property to test. It becomes evidence only when Tracefix runs it and reads the result. The few places a model’s words reach the receipt are marked below, and none of them can raise a level.

A model may write

  • The reproduction test: one pytest file meant to fail before the fix and pass after it.
  • Mutants: small edits to the fixed lines, to see whether the tests notice.
  • Properties, input strategies and examples for Break My Fix.
  • Labels on behaviour changes: intended or suspicious. A label can only keep L3 out of reach.
  • The receipt’s short summary and a note beside each integrity flag. Display only.

Only our code decides

  • Whether a test failed: the exit code and pytest’s JUnit report, which must agree.
  • Which mutants count (fixed hygiene rules) and which ones the tests killed.
  • Whether a property is allowed: it must quote what it rests on and agree with the project’s own tests.
  • Whether a finding counts: a standalone pytest file that fails on the fixed code, three times in a row.
  • The level, from the stages’ statuses (ladder.py, no I/O), and the GitHub check’s conclusion.
  • Tampering, from file snapshots before and after every run.

The four model roles

Each role’s model, effort and budget can be changed in tracefix.yml or with flags; the receipt records what was used. Defaults: effort medium.

The run. Every stage, in order, every time.

A run takes a repository, the commit before the fix (base), the commit with it (head) and the issue text. Every stage runs whatever the earlier ones found: there is no early exit on a counterexample, so the receipt lists every problem at once. A stage that crashes is marked error and gives no evidence; the run goes on.

  1. Environment

    The base test suite must run, and every changed module must import from the copy under test, not from an installed package. If not, the run stops at L0 and the receipt says why.

  2. Reproduce

    The reproducer’s test must fail on base with a real test failure and pass on head three times in a row. With several tests, each is confirmed alone and the file runs again in reverse order. If no attempt reproduces and the last one fails the same way before and after the fix, the fix does not fix the bug: a counterexample.

  3. Guard

    The fix’s source files get their base content back, the tests stay: the reproduction test must fail, and the PR’s own tests must not all pass. Then up to ten mutants of the fixed lines (fewer than three valid ones is inconclusive): at least 80% must be killed. A failure has to repeat to count.

  4. No regressions

    Tests the PR left untouched that passed on base must still pass on head. A confirmed regression is a counterexample.

  5. Fix-line coverage

    Which of the fix’s lines the reproduction test and the PR’s tests run. Shown in the receipt, never in the level.

  6. Behaviour diff

    The same generated inputs on base and head, at least 50 per changed function with at most 20% lost. Every kind of change must be explained by the issue, a docstring example or the reproduction test; then the Judge may veto.

  7. Break My Fix

    Boundary values, then the adversary’s properties, then a Hypothesis search with shrinking, against the changed functions on head. A finding counts only with the exact input, the outcome and a pytest file that fails on head three times in a row.

  8. Integrity audit

    No model at all. Deleted tests, removed or weakened asserts, new skips, broadened pytest.raises, and special cases for inputs named in the issue or the tests. A candidate becomes a flag only when runs confirm it.

  9. Ladder and receipt

    Pure code reads the stage statuses and climbs the ladder. The receipt is built from the stage results only, and every machine path in it is masked.

The ladder. Computed, never chosen.

Lowest first. Our code climbs from the stages’ statuses: each level needs the one below it, and the first gate that stays shut sets the level. Any counterexample ends the climb, unless the run itself could not finish. A counterexample counts only from a stage whose own status says so, so the findings of a stage with tampering never count. The receipt gives the reasons: what each passed gate showed, then why the next one stayed shut.

Put a real receipt through the ladder

Pick a fixture. Its receipt climbs rung by rung and stops where the evidence stops, with the reasons written in the receipt. The fixtures are small buggy repos with known answers; a receipt that gets one wrong fails the test suite.

Open this receipt

  1. COUNTEREXAMPLE

    Proof against the fix.

    A Break My Fix finding, a confirmed integrity flag, a fix that does not fix the bug, or a confirmed regression. A finding that failed the same way before the fix, on code the fix never ran, is listed apart and doesn’t count.

  2. L0

    Nothing to stand on.

    The tests could not run, a changed module imported from outside the copy, the fix’s diff could not be read, tampering was detected in a stage, or the bug was not reproduced.

  3. L1

    Reproduced.

    A test fails before the fix and passes after it, both by running.

  4. L2

    Guarded.

    L1, and the tests fail when the fix is reverted or mutated.

  5. L3

    No unexplained change in what the behaviour diff observes.

    L2, and our checks allow it: everything changed was compared to the end, enough inputs, every kind of change explained, no docstring example broken, no blind spot. Then the Judge can only veto: every change it is shown needs “intended” from every answer. A fix with no behaviour change needs no Judge.

  6. L4

    Tried hard to break it; nothing broke.

    L3, and the strict gate below holds.

The strict L4 gate

  • Break My Fix found nothing, and skipped no changed function.
  • Every target was attacked to the end with at least 100 inputs of its own.
  • Every target has a model property that constrains its result and passed the checks above. Docstring examples don’t count: each checks one input.
  • Every executable line of the fix inside a function was reached by some attack.
  • The integrity audit and the no-regression check finished clean, or had nothing to check.
  • When the last receipt is replayed, every one of its findings is now fixed.

A weak property, or attacks that never reach the fixed lines, can’t lift the level, so some correct fixes stop at L3.

Tampering
Caps the level at L0 and is listed at the top of the receipt. It never gives a pass, and never lowers a counterexample proven by clean runs.
What L3 claims
No unexplained change in what the behaviour diff observes, not that nothing else changed. The channels it does not observe (databases, network, concurrency, performance and more) are listed in every receipt under unchecked.
What L4 claims
That we tried hard to break the fix and nothing broke. It never means “this is correct”.

Isolation and the tamper watch. Your code and the model’s code run in throwaway copies.

The project’s tests and every model-written test run in a subprocess inside a plain temporary copy of the commit, never in your working copy.

strict Linux with bubblewrap

A read-only system. Only the copy under test and the run’s own scratch folder are writable; the other copies, temp files and your home folder are hidden. No network.

basic everywhere else

The same minus the sandbox, plus a best-effort network block. Fine for code you would run pytest on anyway. The receipt carries a prominent warning; --require-strict refuses to run without bubblewrap.

Every run
A timeout, no standard input, an allowlisted environment (no API keys), its own home and temp folders, and the whole process tree killed at the end.
The tamper watch
Before and after every run: the base and head copies, Tracefix’s own environment, the project’s interpreter and your repository are snapshotted. A change where nothing may change makes the stage invalid: never a pass, never a fail.
Cross-checks
A run whose exit code and JUnit report disagree, or that wrote no report, is an error, not a result.
Untrusted text
Issue text, repository code and test output reach the models wrapped as data, and are never followed as instructions.
Limits
A test runs inside the pytest process and can lie about its own result: isolation stops damage, not lying. Guard’s re-runs, the cross-checks and the receipt naming the model-written test as the oracle limit this. In basic mode, writes outside the watched folders are not seen, and only strict mode guarantees that one run cannot influence the next.

The receipt goes where the fix is reviewed.

The GitHub Action runs Tracefix on a pull request and reports there: a check for CI and a comment for the reviewer. The same receipt is kept as JSON in the run’s artifact, for whoever wrote the fix, person or agent.

  1. A fix is pushed to the pull request.
  2. Tracefix attacks it. A counterexample fails the check, and a Break My Fix finding is noted on the line of the fix its failing call ran.
  3. The author reads the receipt. In this one: the call, what it did, the promise it broke and a pytest file that fails.
  4. After the next push, the last receipt’s findings run again on the new commit, and the new receipt says which ones it fixed.
How it stays safe on pull requests from forks
This receipt in full

Fork pull requests. Code from strangers never meets your key.

A pull request from a fork may come from someone you don’t trust, and the run holds your model key. Trust is decided by our code from the GitHub event, never by an input that could loosen it. Untrusted code runs only inside bubblewrap, and the job that posts results never holds the key.

  1. Skipped by default

    On pull_request, GitHub gives a fork’s PR no secrets. The Action skips it with a notice instead of failing.

  2. A maintainer’s label

    After reading the PR, a maintainer adds the tracefix label. That starts a pull_request_target workflow for the exact commit they saw; if it was force-pushed away, the run is refused.

  3. Base branch only

    The job checks out and installs the base branch, never the PR’s dependencies, and fetches the PR’s commits as git data. It refuses to run if the checkout already holds them.

  4. Strict or nothing

    The run requires strict isolation. Without a working bubblewrap it is refused with the reason, never run at basic.

  5. A report job without the key

    A second job posts the check and the comment. It holds no model key and runs no project code; it validates receipt.json strictly and renders the check and the comment again from it.

  6. One approval per commit

    The label is removed after the run, so each new commit needs a maintainer’s new approval.

What strict isolation does not protect against

  • An escape from bubblewrap, such as a kernel bug: code that escaped could read the key and forge the verdict.
  • A test lying about its own result (above).
  • The base branch’s own dependencies: they are installed and trusted as your code.

The full workflow, line by line: docs/GITHUB_ACTION.md.

What is sent to Anthropic. Excerpts, not your repository.

Model calls go to Anthropic’s API with your own key. Each role is sent only what it needs, cut to a fixed size.

Your API key or GitHub token in any test run: the run’s environment is allowlisted.
Budget
By default at most 40 model calls and 500,000 tokens per run. The receipt records the models used, the calls, the tokens and an estimated cost.
